Before you start

Two rules account for most integration failures with these machines.

An absent field is not a zero value Status messages are partial. A field missing from a message means "unchanged / not reported" — never 0, "", or idle. Treating it as a zero causes state to revert, filenames to blank, and temperatures to vanish.
A successful send is not a successful command Transports report that a message was delivered, not that the printer accepted it. Malformed or unauthorised commands can be discarded with no error anywhere. Verification means reading the resulting state back.

The distinction that trips people up The liveview toggle and Developer Mode are separate switches. Liveview opens the local camera stream and leaves cloud control completely intact — a printer can be cloud-controlled and streaming locally at the same time. Developer Mode is the switch that detaches the cloud.
If a device silently goes offline Putting a printer into local mode makes it stop publishing to the cloud entirely. That is correct behavior, not a fault: a cloud client sees the device go dark with no error and no explanation. Check this setting before debugging anything else.
Naming varies by firmware The local-mode switch is labelled "LAN Only", "Developer Mode", or "LAN Mode" depending on firmware generation, and sub-toggles differ. Treat the behavior — cloud detaches, local broker opens — as the reliable part and the menu wording as firmware-specific.

Firmware date is an independent axis

Firmware released after roughly January 2025 verifies every print-namespace command cryptographically, regardless of which path you are on.

  • Machines whose firmware predates that gate accept unsigned commands; after a firmware update they will not.
  • system (lights) and pushing (status requests) are never verified — which is why a light toggle can work while every movement command fails.
  • Signing works over the cloud connection, so no local access is required to use it.

The U1 is local-only: Klipper with the Moonraker API on port 80, no cloud dependency. An access code may optionally be configured; whether the firmware enforces it is unconfirmed, so test against your machine rather than assuming either way.

A second listener exists Port 8883 accepts TLS but terminates the handshake demanding a client certificate. It is not the Moonraker API and is not needed for normal control.

An open port is not evidence a path is usable The local MQTT port is open even when third-party clients are refused. Authentication behavior, not port reachability, is the signal.
Port 6000 is single-session — a scan cannot tell you if it is free The camera service accepts one client. While a session is live, further connection attempts are silently dropped: no SYN-ACK, no RST — which scanners and connect() probes report as "closed", indistinguishable from a disabled listener. Measured on a P1-class unit: an established session streaming ~58 KB/s while fresh SYNs timed out at 6 s, while 80/322/3000 returned RST and 8883 completed. An idle camera port does answer SYNs.

So "6000 is closed" is not evidence the camera is unavailable, and "6000 is open" is not evidence it is free. Confirm by completing the TLS handshake and reading a frame — and check no other client, including a second dashboard instance, already holds it.

Bambu authentication

Three separate credential contexts. Conflating them is the most common early mistake.

Flow 1 — Cloud account

1
Password login POST https://api.bambulab.com/v1/user-service/user/login with {"account","password","apiError":""} → accessToken. Base is .cn for China accounts.
2
Two-factor, if enabled POST /v1/user-service/user/sendemail/code with {"email","type":"codeLogin"}, then re-POST the login with {"account","code"}. The 2FA response may omit success — treat any non-empty accessToken as success.
3
SSO accounts Google/Apple accounts generally cannot use password login. Fallback: read the eyJ… JWT from the web app's localStorage and use that as the access token.
4
Get the uid GET /v1/design-user-service/my/preference → numeric uid, needed for the MQTT username.
5
List devices GET /v1/iot-service/api/user/bind → dev_id (= serial), dev_access_code, model names. A device-list call is also the most effective token validity probe — it fails loudly on a dead token.
Two token species share one field The login service returns an opaque string (~144 chars, not a JWT). An SSO-derived browser token is a JWT. Both are valid in the same slot and both work as the MQTT password. Never assume either shape.
Token expiry is usually unusable A stored expiry of -62135596800 is the Unix timestamp of a zero time value. Clients that ignore non-positive expiry treat the token as valid forever and never refresh. Design for the token dying silently and validate at startup with a device-list call.

Flow 2 — Device access code

The access code is the device credential for all local access (MQTT, RTSPS, camera). It is shown on the printer's LCD under Settings → Network, and is also returned as dev_access_code. Whether the two always match is unconfirmed — see open questions.

Derive IDs from the full serial Truncating a serial to build a local identifier causes distinct devices to silently overwrite one another.

Acks exist — on the report topic There is no separate ack topic, but the firmware replies with result / reason / err_code inline on report, interleaved with status. Register the waiter before publishing, keep ack timeouts non-fatal, and never route an ack into status parsing — an ack carries no home_flag, which a naive parser reads as zero and reports a homed printer as unhomed.
A topic that silently does nothing device/<serial>/mqtt is accepted on connect but silently ignored as a command topic. Using it produces no error and no effect.

Forcing a full snapshot

// publish → device/<serial>/request
{"pushing":{"command":"pushall","version":1,"push_target":1}}

Send on connect. A periodic re-request is also needed — some models publish almost nothing unprompted, so state can go permanently stale. Gate it on a genuinely quiet period, not a fixed timer: frequent pushall is reported to disturb P1P-class hardware.

Command signing

The headline Firmware after roughly January 2025 verifies every print-namespace command. Unsigned ⇒ rejected with err_code 84033543. Developer Mode does not remove the requirement in practice, and signing works over the ordinary cloud connection.

The envelope

// 1. payload — user_id is a top-level SIBLING, not inside "print"
{ "print": { "sequence_id": "5000", "command": "gcode_line", "param": "G28\n" },
  "user_id": "<numeric uid>" }

// 2. sign the exact bytes you will publish
sign_string = base64( RSA-SHA256( privateKey, payload ) )

// 3. append the header, publish unchanged
{ ...payload, "header": { "sign_ver":"v1.0", "sign_alg":"RSA_SHA256",
  "sign_string":"<base64>", "cert_id":"<hex serial>CN=<issuer CN>",
  "payload_len":"<byte length as a JSON STRING>" } }
payload_len must be a string A number yields 84033547, indistinguishable from a certificate problem. The easiest detail to get wrong.
cert_id is a serial, not a hash Lowercase hex X.509 serial + CN= + issuer common name. Vendor IDs are 32 hex because their serials are 16 bytes.
sequence_id ≥ 2000, as a string A fixed floor, not a high-water mark. Below it you get 84033545 even with a trusted certificate.
Signed bytes must equal published bytes Re-serialising after signing changes key order or spacing and breaks verification. Build once, sign, publish unchanged.

err_code ladder

CodeMeaning
84033543No signature present
84033544Contested: file-verify stage, or sequence_id reuse across restarts
84033545Signature valid, cert not trusted — also a trusted cert with sequence_id < 2000
84033546Header field missing or malformed
84033547Signature rejected — wrong key, wrong bytes, or numeric payload_len

Trust store

  • security.app_cert_install installs {command, sequence_id, app_cert, crl} and is itself unverified — that is what makes bootstrapping possible.
  • crl must be non-empty, but its signature is not validated.
  • The store is in RAM and a reboot clears it. Install on every connect, not once at setup. Right after a reboot, listing certs answers device-endreaddevcertfailed.
  • Installation adds; there is no per-certificate removal.
  • Firmware predating the gate does not answer app_cert_list at all.
Adoption without knowing the firmware Send the first print command unsigned. An 84033543 reply means "sign from now on" — retry signed. Machines predating the gate never pay a rejected command.

The trailing newline is required Every gcode_line payload ends with \n inside the param string.
The light command silently no-ops Firmware discards a light command missing sequence_id, led_on_time, led_off_time, loop_times, or interval_time. The publish succeeds, no error appears anywhere, and the light does not change. Treat "missing required field ⇒ silent ignore" as a general pattern for this firmware. Live light state is in print.lights_report, never in the acknowledgement.
Jog convention Switch to relative (G91), emit one G1 with only the axes that actually move — omit the term rather than writing Z0 — then restore G90. Leaving a printer in relative mode is a persistent, hard-to-spot fault.
Movement-safe states A finished print parks the toolhead and is as safe to move from as an idle machine. Gating on "idle" alone breaks on models that omit gcode_state from deltas, since such a printer can stay latched on complete indefinitely. Treat idle and complete as movement-safe.

Telemetry

Reports arrive on device/<serial>/report. Top-level keys: print, camera, system. A message with no print key is valid — ignore it for status.

The presence rule Only update a field when the key was actually present in that message. Represent "not reported" as an explicitly nullable value and render it as —, never 0 or off.

Some firmware resolves a condition by stopping sending the key rather than sending an empty value — so state must decay after a couple of healthy reports, not only on an explicit clear.

Exception: home_flag is a plain integer on the wire, not optional. It is applied on every report that carries it, which is exactly why an ack (which omits it) must never reach status parsing.

State map

RUNNING / PREPARE → printingPAUSE → paused SUCCESS / FINISH → completeFAILED → error IDLE / STANDBY / "" → idle

SUCCESS → IDLE flicker Firmware reports SUCCESS then settles to IDLE on the very next message. Applying that immediately makes "complete" flash and vanish. Require two consecutive idle reports before overwriting a latched complete; any non-idle state should still override instantly.

info.temp is packed

current °C =  value & 0xFFFF
target  °C = (value >> 16) & 0xFFFF

A reported 3932184 is exactly (60<<16)|24 — target 60 °C, current 24 °C. Scaling heuristics produce plausible but wrong numbers. Suspect bit packing before suspecting a unit scale.

print_error lies in both directions ① A print can fail with print_error at 0 the whole time — that class surfaces only through HMS.
② print_error = 83935249 (0x0500C011) is an SD-card advisory, not a job fault, and will hold a healthy printer in an error display.
Correct policy: print_error outranks gcode_state only when gcode_state is present and unhealthy; otherwise surface it as a non-blocking advisory. A latched error nothing can clear is worse than a missed one.

HMS codes

// print.hms — no severity field on the wire
{ "attr": 201327360, "code": 196615 }

human id = "HMS_%04X-%04X-%04X-%04X" % (attr>>16, attr&0xFFFF, code>>16, code&0xFFFF)
module   = (attr >> 24) & 0xFF      severity = code >> 16

Severity 1 or 2 should trip an error state independently of print_error and gcode_state — this is the only channel that reports cover-off and disturbance failures. Unknown module bytes should map to "unknown", which is correct rather than a bug.

HMS_0500-0500-0001-0007 is the signature gate "MQTT Command verification failed. Please update Studio…" — this is a rejected print command raising HMS, which sets state to error, which blocks the movement gate. The visible symptom is that every movement control appears dead. Signing resolves it. The stock message text is written for the vendor's own apps and is not diagnostic.

Camera

Two entirely different local protocols, selected by model class. RTSPS on 322 requires the liveview toggle; the binary protocol on 6000 is single-session and cannot be probed with a scanner.

Model classProtocolNeeds liveview?
H2-class, X1-class, P2S, X2Drtsps://bblp:<code>@<ip>:322/streaming/live/1yes — 322 is closed otherwise
P1-class, A1-classbambus://<ip>:6000?token=<code>observed working with liveview off; whether the toggle affects it is unconfirmed. One client at a time.

RTSPS on 322

  • Username is the literal bblp; password is the access code.
  • H.264 over TLS — browsers cannot display it directly; transcode to MJPEG or HLS.
  • Self-signed certificate; verification must be disabled.
  • Only /streaming/live/1 is known to exist. Verify any other path with an RTSP client.
Raw DESCRIBE redirects in a loop Direct probing returns 301 Moved Permanently → rtsps://<ip>/1 for every path, and the target port is closed. Established RTSP clients still work, so write your own client only after capturing the request sequence one of them uses.

bambus:// binary on 6000

Raw TLS socket, custom framing, roughly one frame per second. Sequence: TCP → TLS (self-signed) → 80-byte auth packet → continuous frames.

header / magic username bblp access code


frame: 16-byte header — [0:4] uint32 LE payload size | [4:7] 0 | [8:11] 1 | [12:15] 0
       then payload_size bytes of raw JPEG (FF D8 FF … FF D9)


Cipher constraint
Some models offer only TLS_RSA_WITH_AES_256_GCM_SHA384 on 6000 — a static-RSA suite excluded
from some TLS stacks by default. It must be explicitly enabled, with the remaining defaults re-listed,
or the handshake simply fails.


Framing has no validation and no resync
Header bytes 4–15 and the JPEG markers are not checked, there is no maximum frame size, and the read
deadline is cleared after the first frame. A desync or a silently stalled camera blocks indefinitely.
Connections keyed by host:port alone reuse a stale connection after an access-code
rotation.





AMS & filament


// print.ams — note the mixed types
"ams": { "ams": [{
    "id": "0",            // STRING
    "humidity": "4",      // index 0-5, lower=drier. ABSENT on AMS 1
    "humidity_raw": "23", // %. ABSENT on AMS 1
    "temp": "25.0",       // °C. ABSENT on AMS 1
    "tray": [{ "id": "0", "state": 3,   // NUMBER: 0 empty, 2 loaded, 3 ready, 10 reading, 11 loaded+data
      "tray_type": "PLA", "tray_color": "000000FF", // RRGGBBAA
      "nozzle_temp_min": "190", "nozzle_temp_max": "230", // STRINGS
      "remain": 750 }],        // NUMBER, mm
  }], "tray_now": "0" }        // (ams_id*4)+tray_id; 254 external, 255 none


Mixed types are a parse hazard
A type mismatch aborts the parse of the entire report, not just the AMS section — one wrong type
silently kills all status for that message.


"Loaded" cannot be derived from state alone
Some units report state: 0 for every tray, including loaded ones. Use
loaded = state ∈ {2,3,10,11} OR tray_type != "". The fallback is safe because units that
report state correctly send tray_type: "" for genuinely empty trays.


Delta vs full updates — merge, never replace
Some units send deltas: an ams object with an empty inner array (only
tray_now changed), or unit objects lacking the tray array (only humidity
changed). Replacing cached state erases filament type, color and remaining length on nearly every
message. Merge units by id and trays by index; retain cached entries absent from a delta;
an empty tray array means keep the cached trays; update the active tray only when
tray_now is non-empty.

The routinely exercised path is the unauthenticated one, and stock Moonraker uses a different parameter

When appending access_code, use & if the URL already has a query string.

Moonraker returns HTTP 200 with an embedded error

{"error": {"message": "Klippy Not Connected"}}

This arrives with a 200 status. Any caller trusting the status code alone reports success for a
failed operation. Check every response body for an error field, not just the G-code
path.


The WebSocket needs a subscribe handshake
Moonraker emits no status until a client sends the JSON-RPC printer.objects.subscribe
message. Without it the socket is silent. A client parsing frames as the flat /api/printer
shape rather than notify_status_update also sees nothing. And if the read deadline is
shorter than the ping interval, a quiet connection always times out before the next keepalive — set the
read wait longer than the ping period. Keep a polling fallback regardless.


State mapping


Flags take priority over text: printing→printing, paused→paused,
error→error; else text Operational→idle, Printing,
Paused, Error, Complete/Cancelled→complete.


Matching is case-sensitive on the OctoPrint-cased strings. Anything unmatched becomes
unknown, which will block movement controls if the UI gates on state.
