1The mental model

Three printers, three completely different control planes. The single biggest source of confusion is that "Bambu printer" does not describe one protocol — and that mode changes behavior more than model does.

Bambu P1S

Stock, pre-Bambu-Connect firmware. Cloud MQTT only. Camera is a bespoke binary-TLS protocol on port 6000. AMS 1 sends delta updates with no humidity/temp.

Bambu H2S

Bambu Connect from day one. Cloud MQTT for control, but camera needs a LAN path: RTSPS on port 322. AMS 2 Pro sends full updates with humidity + temp.

Snapmaker U1

Paxx custom firmware = Klipper + Moonraker. Plain HTTP on port 80, no cloud at all. OctoPrint-style shims mixed with native Moonraker routes.

The five lessons that cost the most time

Lesson 1 — Absent ≠ zero Bambu reports are partial. A heartbeat omits most fields. Treating a missing field as 0/""/idle causes the entire flicker bug family: state reverting, filenames blanking, temps showing ?. Only write a field when the key was actually present.
Lesson 2 — "LAN Only Liveview" ≠ "LAN Mode" Two different toggles. Liveview opens RTSPS:322 for the camera and cloud MQTT keeps working. Full LAN Mode makes the printer stop publishing to the cloud entirely — it goes dark for any cloud client, by design, with no error.
Lesson 3 — Modern firmware cryptographically verifies commands Post-Jan-2025 Bambu firmware rejects every unsigned print-namespace command (err_code 84033543). The fix is an RSA-SHA256 header envelope — not Developer Mode, which only makes the header optional. Acks do exist: they arrive inline on the report topic. See §8b.
Lesson 4 — Numbers lie, strings hide Bambu packs two temperatures into one integer. AMS mixes string and numeric types in the same object. Snapmaker returns HTTP 200 with an embedded error body. Status codes are not evidence of success.
Lesson 5 — Model codes ≠ marketing names O1S is the H2S. BL-P001 is the X1 Carbon. Matching on display names silently misroutes cameras to the wrong protocol and port.
Bonus — Firmware can just stop talking Some firmware resolves an HMS condition by stopping sending the key rather than sending an empty array. If you only clear on explicit hms:[], the printer latches into error forever.

The normalization contract

Every driver must fill one PrinterStatus. Two design decisions are worth stealing:

  • Temperatures, light_on, homed are nullable. null means "unknown / not reported / unsupported" and must render as —, never as off or 0. Rendering null as "off" told users their physically-on light was off.
  • Capability flags beat inference. has_chamber is set by the driver from the model code — not inferred from a nil chamber temperature, because nil only means "not this cycle".
Interface smell worth knowing SetHomed(*bool) exists on the vendor-neutral interface purely because Paxx cannot report homed state. On Bambu it is a no-op. Sometimes a vendor-specific hole has to be poked through a neutral abstraction — but name it honestly so nobody thinks it's universal.

No client spoofing required There is no X-BBL-Client-* or User-Agent impersonation anywhere, and every account endpoint works fine with Go's default client UA. Those headers only matter for the slicer-plugin resource feed. Don't hunt for a requirement that doesn't exist.

Two token species, one slot Confirmed

The MQTT password is literally the same string used as the HTTP Bearer value. But that string can be either of two different things:

① Opaque login token

What /user/login returns as accessToken. Real sample begins AQBK…, ~144 chars, not a JWT.

② Browser JWT

eyJ… pulled from localStorage after an SSO sign-in. Required when the account uses Google/Apple SSO, where password login is impossible.

Gotcha — expiry is usually unknown, and "unknown" means "valid forever" A real token file contained "expires_at": -62135596800 — that is Go's time.Time{}.Unix(). Loaders ignore non-positive values, so expiry stays zero and the validity check returns true unconditionally: nothing ever refreshes proactively. The only thing that catches a dead token is a device-list call failing at startup. Community reports put lifetime around 3 months. Design for "token dies silently", not "token refreshes".
Gotcha — 2FA responses omit success After the 2FA leg the API may return an accessToken while omitting the success field. Treat any non-empty accessToken as success or login fails spuriously.

Token cache: ~/.printer-dashboard/bambu_token_<email>.json (@→_at_, .→_dot_ — despite a comment calling it a hash), schema {token,user_id,region,email?,expires_at}, dir 0700 / file 0600.

There is no separate ack topic — but acks do exist publishCommand returning success only means the broker accepted the publish. The firmware's result/reason/err_code reply arrives inline on the report topic, interleaved with status — so you must demultiplex acks from status and register a waiter before publishing. Forcing a full snapshot: pushall

// publish → device/{serial}/request
{"pushing":{"command":"pushall","version":1,"push_target":1}}

Sent immediately after subscribe to get current state. But it fires only after a genuinely quiet window, because an indiscriminate pushall can stall P1P-class hardware. Do not add a naive timer.

6Command catalog

Exact bytes. Click a command to copy it.

Read §8b first Everything below in the print namespace is rejected outright on post-Jan-2025 firmware (H2S) unless wrapped in an RSA-SHA256 header envelope. What is shown is the inner payload; signing wraps it. system and pushing stay unsigned.
The most expensive gotcha in the repo — ledctrl Bambu firmware silently ignores a light command that is missing sequence_id, led_on_time, led_off_time, loop_times, or interval_time. MQTT publishes fine. No error anywhere. The light doesn't change. This cost a full debugging session. Assume "missing field ⇒ silent ignore" is a general Bambu pattern, not a light-specific quirk.
sequence_id — the old "probably inconsequential" note is superseded print-namespace commands historically omitted it and the system light command sets "0". That is still fine for unsigned frames. But on signed frames a sequence_id string ≥ 2000 is mandatory — below the floor the printer returns 84033545 even with a trusted certificate. sign() injects one when the command builder omitted it. See §8b.
Jog convention worth copying verbatim Switch to relative (G91) → emit one G1 containing only axes with non-zero deltas (omit the axis term rather than emitting Z0) → restore G90. Leaving a printer in relative mode is a nasty latent bug. Note the trailing \n on every Bambu gcode_line.

The SUCCESS → IDLE flicker Firmware reports SUCCESS when a print finishes, then settles to IDLE on the very next push. Applying that immediately makes "complete" flash and vanish within ~2 reports. Fix: require 2 consecutive idle reports before overwriting a latched complete; any non-idle state still overrides instantly.

Related subtlety: CurrentFile is deliberately keyed off the raw per-report state, not the latched one — so the filename clears one report before the COMPLETE badge. That asymmetry is intentional, to decouple the two timings.
print_error misleads in BOTH directions ① False negative: a P1S print failed because the cover came off; print_error was 0 the whole time. That class surfaces only through HMS.
② False positive: print_error=83935249 (0x0500C011) froze a healthy P1S in error. It is an SD-card-degradation advisory from the vendored device_error table — Bambu Handy shows nothing because it arrives on the print_error channel while hms was [].
Correct policy: print_error outranks gcode_state only when gcode_state is present and unhealthy; otherwise it is a non-blocking advisory. A latched error nothing can un-latch is worse than a missed one — the old clear path was gated on State != "error", so even a restart did not help.

info.temp is a packed integer

current °C =  value & 0xFFFF
target  °C = (value >> 16) & 0xFFFF
Forensic proof The original bug report showed a chamber reading of 3932184. That is exactly (60 << 16) | 24 → target 60 °C, current 24 °C. The first attempted fix — "divide by 100000 if > 500", which produced a plausible-looking 39.3 °C — was wrong. Suspect packing before you suspect a unit scale.

8HMS decoding

Bambu's Health Management System is an independent error channel with a bit-packed wire format and no severity field.

// print.hms — plain integers, no severity on the wire
{"attr": 201327360, "code": 196615}

human    = "HMS_%04X-%04X-%04X-%04X" % (attr>>16, attr&0xFFFF, code>>16, code&0xFFFF)
module   = (attr >> 24) & 0xFF   → {0x05 mainboard, 0x0C xcam, 0x07 ams, 0x08 toolhead, 0x03 mc}
severity = code >> 16            → {1 fatal, 2 serious, 3 common, 4 info}
  • Severity 1 or 2 trips State="error" independently of print_error and gcode_state. This is the only channel that catches cover-off / disturbance failures.
  • The module table is deliberately non-exhaustive; unknown bytes → "unknown". That is correct, not a bug.
  • Vendored message table: 4998 device_hms + 946 device_error entries; the device_error half is never queried. Unrecognized codes → empty message, which is expected.
  • Real example: attr=0x03001200, code=0x00020001 → HMS_0300-1200-0002-0001 serious — "The front cover of the toolhead fell off."
Absent ≠ empty — and firmware may just stop talking hms: [] is the explicit clear signal; an absent key must not wipe reported state. But some firmware resolves a condition by simply stopping sending the key. Clearing only on explicit [] latches the printer into error forever. Fix: decay after 2 consecutive healthy reports that omit hms.
We got this one wrong the first time: HMS_0500-0500-0001-0007 "MQTT Command verification failed. Please update Studio (including the network plugin) or Handy…" An earlier write-up here called this an unfixable firmware client-identity gate and said to dismiss it. Wrong. It is the command-signature gate from §8b: a rejected print command raises this HMS, which sets state:"error", which blocks the movement gate — so it presented as "all move buttons are dead". Signing fixes it. Two operational notes: the dismiss endpoint only suppresses notifications, not the state; a printer restart does clear it. The stock message text is aimed at Bambu Studio/Handy and is not diagnostic.

8bCommand signing Confirmed

The single most important protocol discovery in the project — and it overturned a conclusion previously recorded here.

The headline Bambu firmware released after roughly January 2025 cryptographically verifies every MQTT command in the print namespace. Unsigned ⇒ rejected with err_code 84033543 ("mqtt message verify failed").
  • Developer Mode is NOT required. It only makes the signature envelope optional.
  • The P1S accepts unsigned frames only because its firmware predates the gate — it will start rejecting them after a firmware update.
  • system (e.g. ledctrl) and pushing (pushall) are not verified. That is why the light always worked while movement never did.

The envelope

// 1. payload — user_id is a TOP-LEVEL SIBLING, not inside "print"
{ "print": { "sequence_id": "5000", "command": "gcode_line", "param": "G28\n" },
  "user_id": "1578637590" }

// 2. sign the BYTE-EXACT JSON of that object — no canonicalisation
sign_string = base64( RSA-SHA256( privateKey, payload ) )

// 3. append the header, publish the result UNMODIFIED
{ ...payload, "header": {
    "sign_ver": "v1.0", "sign_alg": "RSA_SHA256",
    "sign_string": "<base64>",
    "cert_id": "<lowercase hex serial>CN=<issuer CN>",
    "payload_len": "<utf8 byte length as a JSON STRING>" } }

payload_len must be a string

A number yields 84033547 — indistinguishable from a bad certificate. The easiest detail to get wrong and the most expensive.

cert_id is a serial, not a hash

Lowercase hex X.509 serial + CN= + issuer CN. Bambu's own IDs are 32 hex because their serials are 16 bytes. Every fingerprint-based theory was wrong.

sequence_id ≥ 2000 on signed frames

A string, and a fixed floor — not a high-water mark. Below it the printer answers 84033545 even with a trusted cert. Studio uses a 20000–29999 window.

Sign the exact wire bytes

The signature covers the envelope minus header, including the trailing user_id sibling, and the printer re-checks byte-exact bytes. So sign() splices the header on rather than re-marshalling.

err_code ladder — 84033543–84033548 are one family

err_codeMeaning
84033543No signature present → triggers signing auto-detection
84033544Contested: file-verify stage (bad md5, plaintext url, ftp:///) or sequence_id reuse across restarts
84033545"need reset device pub key" — signature valid, cert_id not trusted; also a trusted cert with sequence_id < 2000
84033546Required header field missing or malformed
84033547Signature rejected — wrong key, wrong bytes, or numeric payload_len

The trust store

  • security.app_cert_install installs {command, sequence_id, app_cert, crl} and is itself not verified — that is what makes bootstrapping possible.
  • crl must be non-empty (empty ⇒ "crl value is null") but its signature is not validated, so a self-minted CRL is accepted.
  • The store lives in printer RAM and a reboot clears it. So install on every connect, not once at setup. Right after a reboot app_cert_list answers device-endreaddevcertfailed.
  • Install adds; there is no command to remove a single cert.
  • A cert only needs installing — it need not have been provisioned through Bambu's cloud. But an arbitrary self-signed cert still fails signing with 84033547, so the chain is enforced. The own-key shortcut does not work.
  • The shared Bambu app cert/key have been public since January 2025 (extracted from Bambu Connect, embedded in every copy). Not secret, not user-specific. Its 2025-12-12 expiry is not enforced. Cached to the data directory as bambu_app_{cert,key,crl}.pem so an operator can replace them without a rebuild.

Acks do exist — a previous conclusion here was wrong

Earlier research in this repo concluded firmware acks were infeasible on cloud MQTT. Incorrect. The firmware replies with result/reason/err_code inline on the same report topic, interleaved with status. So:

  • Register a waiter before publishing; turn a non-success ack into an error. Keep timeouts non-fatal so printers that never ack aren't falsely blamed.
  • Never let an ack fall through into status parsing. An ack carries no home_flag, which reads as zero and silently marks a homed printer unhomed.
Runtime adoption The first print command goes out unsigned; an 84033543 flips signRequired and retries signed. Printers predating the gate never pay a rejected command, so the P1S is behaviourally unchanged. commandRejectedError carries the numeric err_code so callers branch on the verification family instead of matching message text.
Already ruled out — don't re-test Identical failure over cloud and LAN, so transport/encoding/topic/payload are all excluded — the cloud is a forwarder, not a different command language. Eleven gcode_line payload variants all produce the same rejection when unsigned: payload shape does not influence verification. Chain-of-trust theories were refuted (a real Bambu-chain cert failed identically while payload_len was still numeric).

10Three camera protocols

The most expensive reverse engineering in the project. Three printers, three completely different video paths.

Not HTTP. Raw TLS socket with custom binary framing. bambus://<ip>:6000?token=<access_code>

Sequence: TCP dial → TLS handshake → send 80-byte auth packet → receive continuous frames at ~1 FPS.

Auth packet — 80 bytes, little-endian

header / magic username bblp (16–47) access code (48–79) 


Unexplained magic constants
0x40 (64) ≠ 80 and 0x3000 (12288) are magic. Nobody here derived them.
Don't "clean them up".



Frame format


16-byte header:  [0:4] uint32 LE payload size | [4:7] 0x00 | [8:11] 0x01 | [12:15] 0x00
then payload_size bytes of raw JPEG (FF D8 FF … FF D9)



The H2S/O1S cipher trap
H2S/O1S printers on port 6000 offer only TLS_RSA_WITH_AES_256_GCM_SHA384 — a
static-RSA suite that Go excludes from its defaults. You must hand-list it, and re-list Go's
other defaults explicitly or you lose forward secrecy on everything else. Without this the handshake
just fails. Hard-won.



Framing has no validation and no resync
Header bytes 4–15 and the JPEG FFD8/FFD9 markers are documented but
never checked; only payloadSize == 0 errors. There is no resync and no max frame
size, and the read deadline is cleared after the first frame. A desync or a silently-stalled
camera blocks forever and only recovers via reconnect backoff (1 s→30 s). Also: connections are keyed
by host:port only, so a rotated access code reuses the stale connection until
restart.

waitForReady — a browser aborting during the 10 s readiness window kills the instance that
just started and returns 502, despite a prominent comment insisting subprocesses never inherit request
contexts.

② The helpful 501 install go2rtc branch is unreachable in production (the server
always allocates a non-nil manager), so a missing binary surfaces as an opaque 502 — which is exactly
how the misdiagnosis above happened.


The flicker that wasn't an error
The famous "camera flicker" was the handler serving a gray 1×1 placeholder with 200 OK
on transient failure. The browser's onload fired happily — a success that looked
like a broken stream. Fix: last-good-frame cache + only serve frames that actually parse as JPEG.
When a stream flickers, check whether you're being handed a valid placeholder.


Separately: browsers cancel in-flight image loads constantly. Those surface as
context canceled / context deadline exceeded and were being reported as auth
failures. Use a dedicated 15 s timeout context and filter those out of the error state.


Proxy has no auth gate
GET /api/camera/proxy?url=… and GET /api/camera/frame dispatch on scheme
(http/https passthrough, rtsps→go2rtc, bambus→buffer,
else 501) with only no-cache middleware. This is LAN-trust by design — if you expose the dashboard
beyond the LAN, the camera proxy is an unauthenticated window into your printers.







Bambu's remote camera uses proprietary TUTK P2P. Credentials come from
POST /v1/iot-service/api/user/ttcode → {ttcode, authkey, passwd, region}
(plus stream_key, stream_salt, channel_name, app_id).


Status: implemented, then abandoned — zero production callers. GetTTCode,
StartTUTK, LoadLibrary are all uncalled dead code. LAN-only was sufficient.


The cost of picking this back up
The official plugin (libBambuSource.so, liblive555.so) is fetched at build
time from api.bambulab.com/v1/iot-service/api/slicer/resource?slicer/plugins/cloud=02.07.00.00
— that endpoint does require X-BBL-Client-* headers. The cgo binding was written
arm64-only and never compiled for amd64 until multi-arch CI enabled it, which then produced three
separate build breaks: a Go reserved-keyword struct selector (info.type → cgo renames
it ._type), a missing #include <unistd.h> for usleep, and an
anonymous C union that cgo maps to [12]byte with no Go representation, requiring an
unsafe.Pointer reinterpret. Expect that class of problem.

11Snapmaker U1 · Paxx firmware


"Paxx" is the community firmware — but what it actually is turned out to be the
biggest surprise: Klipper + Moonraker.



The founding wrong assumption
The original client assumed a flat "Paxx REST API". It was wrong and the client was rewritten. The
practical consequence: the API surface is a hybrid of OctoPrint-style shims and true Moonraker
routes, and you must know which is which. Default port is 80, not 8080.

The WebSocket is decorative

    

  • No Moonraker JSON-RPC printer.objects.subscribe handshake is ever sent — and
Moonraker emits nothing meaningful without it.
    • 

  • The read loop parses frames as the flat /api/printer shape, not
notify_status_update.
    • 

  • wsReadWait (10 s) is shorter than wsPingPeriod (30 s), so a pong can
never rescue the read deadline — a quiet connection dies ~10 s after any frame.
    • 

  • The 3 s REST poll ticker runs unconditionally, because the WS path carries no
gcode_move data at all.
    • 


Net effect: all real data comes from 3-second REST polling. WS errors are never logged or
surfaced. If you're debugging "why isn't Snapmaker pushing", this is why.



Latent bug — auth corrupts Moonraker query URLs
The request builder appends ?access_code=… unconditionally. The objects-query path
already contains a ?, so with an access code configured the URL becomes
…gcode_move?access_code=X, corrupting the last object name. Untested; silently degrades
progress/layers/Z-position. Use & when a query already exists.



Moonraker returns HTTP 200 with an embedded error
A body like {"error":{"message":"Klippy Not Connected"}} arrives with a 200 status.
Only the gcode path checks for this. Pause/resume/cancel, skip-object, and both fetch paths do
not — so a Klipper-side failure on pause reads as success. Assume any Moonraker call can
lie this way.

LED state is unqueryableMoonraker's led object query always returns null for cavity_led. Real state cannot be read — store the last commanded state.

matters to you, this is real work, not a config issue.

      "tray_type": "PLA", "tray_color": "000000FF",  // RRGGBBAA
      "tray_info_idx": "GFA00",
      "nozzle_temp_min": "190", "nozzle_temp_max": "230",  // STRINGS
      "remain": 750,          // NUMBER, mm; -1 unknown
      "tray_weight": "250", "tag_uid": "8A160AB5…"
    }]
  }],
  "tray_now": "0",             // (ams_id*4)+tray_id; 254=external, 255=none
  "ams_exist_bits": "1", "tray_exist_bits": "e"  // parsed, never read
}


The type chaos is a parse bomb
A type mismatch aborts the entire report parse, not just AMS — one wrong type kills all printer
status, silently. When adding AMS fields, match the wire type exactly.



The expensive bug: P1S delta updates


P1S sends delta AMS updates; H2S sends full updates. A P1S delta may arrive as
ams present with an empty inner array (only tray_now changed), or with
unit objects that lack the tray array (only humidity changed). Naive
"replace cached AMS" logic therefore wipes filament type/color/remaining on nearly every report
— and with omitempty the field vanishes from the API response entirely.


Fix: merge, don't replace. Units merged by ID, trays by Index;
cached entries absent from the delta are retained; an empty tray array means keep
cached trays wholesale; scalars use firstNonEmpty(new, cached); and
ActiveTrayID is written only when tray_now is non-empty.


Still open
Research says P1S "must call pushall periodically" — our code sends it exactly
once at connect, with no timer anywhere. Combined with the merge cache, a field missed at startup
can stay wrong until reconnect. Adding a periodic pushall closes it.

16Discovery timeline


How the knowledge was actually earned — including the wrong turns.



  
2026-07-08
Started on LAN MQTT — abandoned same day

    
First Bambu client targeted a local broker on the printer. Rewritten to cloud MQTT the same day
    to avoid requiring LAN/developer mode. This decision shapes everything downstream.

  
2026-07-08
Snapmaker rewritten for Moonraker

    
"The U1 runs Moonraker (Klipper) under the hood, not the flat Paxx API we assumed." Port default
    corrected 8080 → 80.

  
2026-07-08
Partial-report flicker class discovered

    
gcode_file blanking on heartbeat reports led to the pointer-field "only write when
    present" convention that now governs every optional field.

  
2026-07-11
Chamber temp 3932184 → packed integer

    
First fix ("divide by 100000 if >500") gave a plausible 39.3 °C and was wrong. Correct decode:
    (60<<16)|24 = target 60, current 24.

  
2026-07-12
P1S cover-off failure with print_error=0

    
Proved HMS was entirely unparsed. HMS added as an independent error channel — the only one
    that catches this failure class.

  
2026-07-12
ledctrl silent no-op

    
Light toggle did nothing with no error anywhere. Firmware requires five fields; and light
    state lives in print.lights_report, not the system.ledctrl ACK.

  
2026-07-16
WRONG TURN: "verification failed" HMS declared not-our-bug

    
Investigation concluded a firmware client identity/version gate with no app-side fix, and
    concluded ack verification was impossible on cloud MQTT. Both conclusions were later
    overturned. Recorded here because "impossible" claims in a knowledge base are the most
    dangerous thing in it.

  
2026-10-08 → 10-11
Command signing cracked (K-108/K-109)

    
The H2S rejects every unsigned print command because post-Jan-2025 firmware
    verifies them with a key from Bambu's closed-source plugin. Signing with an RSA-SHA256
    header envelope moved it from 84033543 (no signature) to
    84033545 (valid signature, untrusted cert) — proving the mechanism and that
    Developer Mode is not required. Cert installed on every connect because the trust store is
    RAM-only. Home All and jog now work on the H2S.

  
2026-10-08
print_error=83935249 — an SD-card advisory, not a fault

    
A healthy P1S was frozen in error. Three stacked defects: any non-zero
    print_error overrode a healthy gcode_state; nothing could un-latch it;
    and the device_error table was unreachable (wrong key width, and model names needed
    aliasing C12→P1S). Non-zero print_error under a healthy
    state is now a non-blocking advisory.

  
2026-07-29
"H2S camera is disabled" — false alarm

    
Root cause: go2rtc not in PATH for a local binary. Works fine in Docker.
    Follow-up work then filtered browser-cancel errors that were masquerading as auth failures.

  
2026-07-27/30
Paxx homing reality

    
homed_axes not exposed; Z parks at ~9.9 mm so Z can't imply homed; G28
    needs 120 s; "Must home" substring detection added.

  
2026-07-31
X1 misrouting + LAN-Mode silence

    
X1 (BL-P001) was being sent to port 6000; camera routing split from chamber
    semantics. Separately: printers in full LAN Mode go silent on cloud MQTT by design — 60 s
    silence detection added so the failure is at least named.

  
2026-08-02
P1S AMS delta wipe fixed

    
Delta updates with empty inner arrays were wiping cached filament data. Merge semantics added.
    Notable: an earlier spec had signed off "no backend changes needed" while its own open-questions
    section flagged the exact behavior as high severity.
